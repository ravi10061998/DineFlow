# DineFlow

Multi-restaurant ordering, payment & delivery management platform. A monorepo with a Next.js (TypeScript) frontend and a NestJS (TypeScript, TypeORM, PostgreSQL) backend, managed as npm workspaces, built module by module per the platform spec.

```
dineflow/
├── frontend/   # Next.js 16 app (App Router, TypeScript)
├── backend/    # NestJS API (TypeScript, TypeORM, PostgreSQL, dynamic RBAC)
└── package.json  # root workspace scripts
```

## Prerequisites

- Node.js **≥ 20.9** (this repo was set up on Node 24 via `nvm`)
- PostgreSQL running locally (or via Docker) — nothing was installed for you, see below

## 1. Install dependencies

From the repo root (installs both workspaces):

```bash
npm install
```

## 2. Set up PostgreSQL

Create a database for the app. Either with a local Postgres install:

```sql
CREATE DATABASE dineflow;
```

or with Docker:

```bash
docker run --name dineflow-postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=dineflow -p 5432:5432 -d postgres:16
```

## 3. Configure environment variables

```bash
cp backend/.env.example backend/.env
cp frontend/.env.local.example frontend/.env.local
```

Edit `backend/.env` — DB credentials and JWT secrets. Generate real secrets for anything beyond local dev (`openssl rand -hex 64`).

## 4. Run migrations and seed the first admin

The schema is owned entirely by migrations (no `synchronize`) from Module 2 onward:

```bash
npm run migration:run -w backend
npm run seed:admin -w backend   # creates the first ADMIN user — see backend/.env for credentials
```

## 5. Run in development

From the root, runs both apps concurrently:

```bash
npm run dev
```

- Frontend: http://localhost:3000
- Backend: http://localhost:4000/api/v1 (health check at `/api/v1/health`, Swagger docs at `/api/docs`)

Or run them individually: `npm run dev:frontend` / `npm run dev:backend`.

> **Windows note:** Nest's watch-mode restarter shells out to `taskkill` on every file change. If your shell's `PATH` doesn't include `C:\Windows\System32` (true for some Git Bash / restricted PowerShell setups), the restart fails and the *old* process survives as a zombie still bound to port 4000 — serving stale code while looking like everything's fine. Fix: `$env:PATH += ";C:\Windows\System32"` before `npm run dev -w backend`. If you ever get inexplicable stale behavior after an edit, check `Get-NetTCPConnection -LocalPort 4000` for a leftover process first.
>
> **Low-memory note:** this dev machine has 8GB RAM. Running both dev servers plus a `nest build`/`jest` run at the same time can OOM-kill the build (`JavaScript heap out of memory`). If a build/test run crashes for no obvious reason, stop both dev servers first (`Get-Process -Name node | Stop-Process -Force`), run the build/tests, then restart the servers.

## Backend architecture

NestJS, organized per the spec's modular architecture (`src/modules/<name>/{entities,dto}`, `controllers`, `services`). Schema changes are migrations only — see `backend/src/database/migrations/`. `backend/src/database/data-source.ts` is the CLI-only datasource (migrations); the running app gets its TypeORM config from `backend/src/config/typeorm.config.ts` via `ConfigService`.

### Modules built so far

**Module 2 — Users, Roles, Permissions & Auth** (`src/modules/{auth,users,roles}`)
- Fully dynamic RBAC: `roles`/`permissions`/`role_permissions` tables, admin-manageable at runtime. The 5 spec roles (`ADMIN`, `RESTAURANT_ADMIN`, `RESTAURANT_STAFF`, `CUSTOMER`, `DELIVERY_PARTNER`) are seeded as `is_system` roles and can't be deleted/renamed.
- JWT access tokens (15 min) carry the caller's resolved permission list; routes declare requirements with `@RequirePermissions('module:action')`, checked by `PermissionsGuard`. Every route requires auth by default — opt out with `@Public()`.
- Refresh tokens: opaque, hashed at rest, rotated on every use, with theft/reuse detection (reusing a revoked token revokes its whole session family).
- Register/login/refresh/logout/logout-all, email verification, forgot/reset password. Email/SMS sending is stubbed to `console.log` — wire up the real Notifications module (§29) later.
- `npm run seed:admin -w backend` bootstraps the first `ADMIN` user (not a migration — needs bcrypt).

**Module 3 — Restaurant Registration & Approval** (`src/modules/restaurants`)
- Public `POST /restaurants/register` creates a `PENDING` restaurant + its first `RESTAURANT_ADMIN` user atomically, then auto-logs them in (same token shape as customer register).
- Admin lifecycle: `/admin/restaurants/:id/{approve,reject,suspend,block,reinstate}`, guarded by a server-side state machine (e.g. `PENDING→SUSPENDED` is rejected as `INVALID_STATUS_TRANSITION`; `BLOCKED` is terminal). Every transition is recorded in `restaurant_status_history` (who/when/why) — there's no Audit Log module yet, so this table is the only trail restaurant lifecycle changes get for now.
- Self-service `/restaurant/me/*` routes (profile, business hours, holidays, documents) are identity-scoped via `RestaurantMemberGuard` + `req.user.restaurantId` — never the dynamic permission system, since these aren't admin actions.
- Document uploads (`POST /restaurant/me/documents`, multipart) go to local disk (`backend/uploads/`, gitignored), validated by mime type/size, served back only through an authenticated route — never `express.static`. Admin can verify/reject each document.
- Deliberately **not** storing raw bank account numbers on `restaurants` — that belongs in the Payment module's gateway-hosted onboarding (Module 17), not our DB.
- **Restaurant logo** (added later, alongside the dashboard redesign below): `logo_path`/`logo_original_name`/`logo_mime_type` columns directly on `restaurants` (same shape as the customer profile photo, minus the 1:1-table split — `restaurants` is already its own table). `POST`/`DELETE /restaurant/me/logo` (multipart, `RestaurantMemberGuard`) manage it; unlike a customer's own profile photo, it's served through a **public** route (`GET /restaurants/:id/logo`, no auth) since customers need to see it without a session — same reasoning as Module 16's public product-photo route. `GET /restaurants` and every `StoreRestaurant` summary now include a `hasLogo` boolean so the frontend only attempts the image request when one actually exists. A new `GET /restaurants/:id` (public, single-restaurant detail — name/description/city/state/`hasLogo`) followed right after, since the customer-facing menu page had nowhere to show which restaurant it belongs to.
- **Real bug found and fixed while wiring this up**: Helmet's default `Cross-Origin-Resource-Policy: same-origin` header was silently blocking the frontend (a different origin in dev) from loading *any* publicly-served image via a plain `<img src>` — including Module 16's product photos, which had been silently broken since that module shipped (nobody noticed because the graceful placeholder fallback looks intentional either way). Fixed globally in `main.ts`: `helmet({ crossOriginResourcePolicy: { policy: "cross-origin" } })` — every other Helmet protection (CSP, HSTS, frame-options) stays at its default.

**Module 4 — Subscription Plans & Free Trial** (`src/modules/subscriptions`)
- One row per restaurant in `restaurant_subscriptions` (mutable status), append-only `subscription_events` audit log — same pattern as Module 3's status history.
- Trial auto-starts on restaurant approval via an event (`restaurant.status_changed`, `@nestjs/event-emitter`) rather than a direct service call — `RestaurantsService` and `SubscriptionsService` stay decoupled. "Only one free trial ever" is structural: the listener skips if the restaurant already has any subscription row, not just a convention.
- Subscribing snapshots price/commission from the plan server-side (`priceSnapshot`/`commissionValueSnapshot` — the client only sends a `planId`). A later plan price change never retroactively affects an already-subscribed restaurant.
- A daily cron (`@nestjs/schedule`, borrowed early from Module 35 the same way Module 3 borrowed `multer`) expires trials past `trialEndsAt` and logs reminder events at the configured day thresholds.
- Seeded with the spec's own BASIC (₹999/mo, 10%) / PRO (₹1999/mo, 5%) / PREMIUM (₹2999/mo, 0%) example plans so the system is immediately exercisable.
- **Deliberate limitation, flagged**: no payment gateway exists yet (Module 17), so `subscribe` activates a plan immediately instead of going through a pending-payment step.

**Module 5 — Commission System** (`src/modules/commission`)
- `calculateCommission(restaurantId, amount)` resolves the rate through a precedence chain — an active `commission_rules` override beats the subscription plan's snapshot, which beats the trial commission rate — then computes the platform/restaurant split. Percentage: `amount * value / 100`. Fixed: clamped so it can never exceed the order amount (never a negative restaurant payout).
- `CommissionType` (PERCENTAGE/FIXED) moved to `common/enums/` — it's shared between `subscription_plans` and `commission_rules` now, no longer owned by one module.
- A gap in Module 4 fixed here: `trial_settings` gets `trial_commission_type`/`trial_commission_value` columns (§5 always listed "Trial commission rate" as an admin setting; it just hadn't been added yet). Defaults to 0% — trials are commission-free unless admin sets otherwise.
- At most one active `commission_rules` row per restaurant — creating a new one deactivates the prior one in the same transaction, preserving history rather than deleting it (same shape as Module 3/4's audit tables).
- **Deliberate scope limit, flagged**: no `order_commissions` snapshot-per-order table yet — it's meaningless without an `orders` table to reference (Orders is a much later module). What's built now is the calculation engine itself (`CommissionService.calculateCommission`) plus preview endpoints; Orders will call this same service and persist its result once it exists.

**Module 6 — Categories** (`src/modules/categories`)
- Restaurant-owned menu sections (e.g. "Starters", "Main Course") — deliberately *not* a platform-wide cuisine taxonomy for customer browsing/filtering, even though the spec's Admin Panel list mentions "Categories" alongside Products/Coupons. That's a discovery feature with no UI to consume it until the Customer module exists; building it now would be speculative.
- Unique on `(restaurant_id, name)`; a Postgres unique-violation (`23505`) is mapped to a friendly `CATEGORY_NAME_TAKEN` rather than leaking the raw DB error.
- Reordering is a dedicated bulk endpoint (`PUT .../reorder`), not N individual PATCHes — validates the submitted ID list is an *exact* match (same size, no foreign/missing IDs) against the restaurant's own categories before applying anything, so a bad list rejects atomically rather than partially reordering.
- Delete is blocked if any product references the category — a structural no-op today (no `products` table until Module 7) but the guard and its error code (`CATEGORY_IN_USE`) exist now so Module 7 only has to add the real `COUNT` query.
- Admin gets read-only oversight (`GET /admin/restaurants/:id/categories`, new `categories:read` permission); restaurants own full CRUD + reordering via the same identity-scoped `RestaurantMemberGuard` pattern as every other self-service module.

**Module 7 — Products/Menu** (`src/modules/products`)
- `products` (each FK'd to a `category`, `ON DELETE RESTRICT` — a category can't be dropped out from under a live product, backing up the app-level `CATEGORY_IN_USE` guard at the DB level too), plus `product_variants` (mutually-exclusive choice, e.g. Small/Medium/Large — an *absolute* price, not a delta off `base_price`) and `product_addons` (independent multi-select extras, e.g. Extra Cheese — an *additive* price).
- Genuine circular module dependency with Categories, resolved with `forwardRef()` on both sides (both `@Module` imports and both services' constructor injections): `ProductsService.create/update` validates `categoryId` belongs to the caller's restaurant via `CategoriesService.findOneOrThrow`; `CategoriesService.remove` now calls the real `ProductsService.countInCategory()` instead of Module 6's hardcoded-0 stub.
- `isActive` (permanent menu visibility) and `isAvailable` (day-to-day "out of stock" toggle) are deliberately separate booleans — a temporarily 86'd item shouldn't need re-adding, just a `PATCH .../availability`.
- Images are a small `jsonb` array on the product row itself (id/path/originalFileName/mimeType), not a join table — uploaded via `multipart/form-data` (multer `diskStorage`, same 5MB/JPEG-PNG-WebP validation and forward-slash-only stored-path convention as Module 3's documents), served back only through an authenticated route.
- Same exact-match bulk reorder pattern as Module 6, scoped to a category (`PUT .../reorder` with `{ categoryId, orderedIds }`) — rejects atomically if the list doesn't exactly match that category's products.
- Admin gets read-only oversight (`GET /admin/restaurants/:restaurantId/products`, new `products:read` permission); restaurants own full CRUD + variants/add-ons/images/reorder via `RestaurantMemberGuard`.
- Frontend: `/restaurant/products` (grouped by category, inline create form, per-product "Manage" panel for edit/variants/add-ons/photos, up/down reorder scoped within each category) + a read-only products modal on `/admin/restaurants` matching the Categories modal pattern. Product photos render via a small authenticated-blob-to-object-URL helper (`fetchAuthenticatedBlob` in `api-client.ts`) since `<img src>` can't carry a Bearer token.
- **Addendum (2026-08-22)**: the create-product form originally only took name/price/description — a photo could only be added afterward, as a second step, by expanding the product's "Manage" panel. Added an optional photo picker directly to the create form itself: the backend's upload endpoint still only accepts a file for an already-existing product (unchanged, no backend risk), so the frontend now creates the product first and immediately follows with the image-upload call to the newly-returned id, all within one form submission — a genuine one-step create-with-photo from the restaurant owner's side, even though it's two API calls under the hood. A failed image upload is reported without discarding the just-created product (it still shows up in the list, photo-less, with an inline error naming the failure) rather than rolling back a product that was in fact created successfully. Verified visually via Playwright — selecting a real file, submitting once, and confirming server-side (`GET /restaurant/me/products`) that the new product's `images` array was populated, not just a client-side illusion.

**Module 8 — Customer Profile** (`src/modules/customers`)
- Registration/login for customers already worked before this module — `POST /auth/register` has always defaulted new signups to the `CUSTOMER` role, and `/admin/users` already gives admins generic list/status/role management across every role. This module adds only what was genuinely missing: a place for a customer to view/edit profile extras.
- `customer_profiles` is a 1:1 extension of `users` (`user_id UNIQUE REFERENCES users(id) ON DELETE CASCADE`) — kept as its own table rather than columns on `users`, same reasoning as `restaurants` not being columns on `users`. The row is created lazily on first access, not at registration time, so `auth.service.ts` stays untouched.
- New `CustomerGuard` (`/customer/me/*`) mirrors `RestaurantMemberGuard`'s identity-check shape, but keys off `roleName === CUSTOMER` instead of a restaurantId.
- `PATCH /customer/me/profile` can update `users` fields (fullName/phone) and `customer_profiles` fields (dateOfBirth/gender) together in one request — the two-table split is an internal detail, not something the API exposes — wrapped in one transaction so a phone-uniqueness conflict can't leave one table updated and the other not. A `23505` on `users.phone` maps to `PHONE_ALREADY_IN_USE`.
- Profile photo upload/delete/serve follows the exact same multer conventions as every other upload in the app (5MB/JPEG-PNG-WebP, forward-slash stored paths, authenticated file-serving route) — a customer has at most one photo, so uploading a new one deletes the old file.
- Email is deliberately **not** editable here — an email change needs its own verification flow, out of scope for this slice.
- Frontend: `/profile` (photo upload/remove via a circular-avatar `ProfilePhoto` component, account-details form) — the first real customer-facing page beyond auth. Login/register/homepage CTAs now route customers here instead of back to the still-storefront-less homepage.

**Module 9 — Customer Addresses** (`src/modules/addresses`)
- `customer_addresses` reuses the exact field convention already established on `restaurants` (`addressLine1/2, city, state, postalCode, country, latitude, longitude`), plus delivery-specific fields: `label` (HOME/WORK/OTHER), `receiverName`/`receiverPhone` (may differ from the account owner), `landmark`, `deliveryInstructions`, `isDefault`. A soft cap of 20 addresses/customer guards against unbounded growth.
- The first address a customer ever saves is forced to `isDefault=true` regardless of what was requested — there's never a "no default" state right after onboarding. Any operation that changes which address is default (create-as-default, `PATCH .../default`, `PATCH :id` with `isDefault: true`, or deleting the current default) wraps the unset-old + set-new in one transaction so two rows can never both be default; deleting the default auto-promotes the oldest remaining address if one exists.
- Reuses the `CustomerGuard` from Module 8 — no new guard needed. No admin oversight endpoint in this slice (private customer data, no support-tooling need yet).
- `AddressesService` is exported from its module so a later Cart/Orders/Delivery module can resolve a customer's default/selected address without duplicating the lookup.
- Frontend: an "Saved addresses" section added to `/profile` — add/edit/delete, set-default, full address form (`AddressForm`/`AddressList` components).

**Module 10 — Cart** (`src/modules/cart`)
- A single `cart_items` table — no separate "cart" header row, there's nothing to hang off one beyond the items. Deliberately stores **no price**: a cart is pre-commitment, so unit/line prices are computed live from the current catalog on every read; snapshotting happens at Order creation (a later module), not here.
- Restaurant-scoped like most food-delivery apps: adding an item from a different restaurant than what's already in the cart is rejected with the existing restaurant's name (`CART_DIFFERENT_RESTAURANT`) unless the request sets `replaceCart: true`, which clears the old cart in a transaction before adding the new item. `restaurantId` is always derived server-side from the fetched product, never accepted as client input.
- Adding an item merges into an existing matching line (same product + variant + add-on set) instead of duplicating it; validates the product is active/available and that a given `variantId`/`addonIds` actually belong to that product; quantity is capped 1–50 per line.
- A cart line whose product/variant/add-on has since gone inactive is kept but flagged `isAvailable: false`, not silently dropped — the customer sees why before checkout.
- **New minimal public "browse" endpoints** added alongside this module, since Cart is otherwise unreachable from a real UI with no storefront yet: `GET /restaurants` (approved restaurants only) and `GET /restaurants/:id/menu` (active categories + active products, each with their active variants/add-ons). This is deliberately not the full storefront (no search/filters/ratings) — just enough to make add-to-cart possible from a browser.
- Frontend: `/restaurants` (browse list), `/restaurants/:id` (menu with per-product variant/add-on/quantity picker and "Add to cart", including the replace-cart confirmation flow), `/cart` (quantity controls, remove, clear, subtotal, checkout).
- **Menu page redesign** (added later, alongside the restaurant logo work above): the page now opens with a restaurant header card (logo, name, city/state, favorite heart) instead of a bare "Menu" title, using the new public `GET /restaurants/:id` detail endpoint. Each `MenuProductCard` grew a large (112px) product photo — previously a 64px thumbnail wedged next to the text — with the favorite heart floating over it and an out-of-stock item shown dimmed/grayscale rather than just a text label, closer to a real food-delivery app's product listing. The `/restaurants` browse list also gained a small logo thumbnail per row.

**Module 11 — Orders** (`src/modules/orders`)
- Converts a validated cart into an **immutable, money-adjacent** record — the opposite of Cart's deliberately live pricing. `orders` snapshots the delivery address (copied from the selected `customer_addresses` row at checkout — a later address edit/delete never rewrites history) and the commission split; `order_items` snapshots product/variant/add-on names and prices. `customer_id`/`restaurant_id` use `ON DELETE RESTRICT` (financial records must never silently vanish); `order_items.product_id`/`variant_id` stay nullable `SET NULL` since Products already supports hard delete.
- Checkout calls Module 5's `CommissionService.calculateCommission` directly — the exact call that service's own notes flagged as deferred until an `orders` table existed. Rejects if the cart is empty or any line is flagged unavailable (the customer must fix the cart first, nothing is auto-removed).
- Order fulfillment reuses Module 3's exact status-transition pattern: an `ALLOWED_TRANSITIONS` map plus an append-only `order_status_history` table, guard-check + update + history row in one transaction. `PLACED→CONFIRMED→PREPARING→READY→OUT_FOR_DELIVERY→DELIVERED`, with `CANCELLED` reachable from `PLACED`/`CONFIRMED`/`PREPARING` by the restaurant. Customer self-cancel is stricter — only while still `PLACED`.
- `paymentStatus` only ever ends up `PENDING` in this module — wired to a real payment flow in Module 12 right after.
- Small additive change to Module 10 alongside this: `CartLineView.addonNames: string[]` became a richer `addons: {id,name,price}[]`, since Orders needed the per-add-on price breakdown Cart's view didn't expose. Also exported `CartService` (was previously module-private) so Orders' checkout can read the validated, live-priced cart it converts.
- Unlike private customer data (Addresses/Profile), admin gets real oversight here (new `orders:read` permission, `GET /admin/orders`) — orders are platform-relevant financial records.
- Frontend: checkout wired into `/cart` (delivery-address picker), `/orders` + `/orders/:id` (customer order history/detail/cancel), `/restaurant/orders` (fulfillment queue with a "mark next status"/cancel per order), `/admin/orders` (read-only table).

**Module 12 — Payment** (`src/modules/payments`)
- No real gateway credentials exist in this dev environment, so this builds the **correct architecture** instead of a fake shortcut: a swappable `PaymentGateway` interface, backed by `MockPaymentGateway` — shaped exactly like a real Razorpay/Stripe adapter (an order-creation call, then `HMAC-SHA256(gatewayOrderId|gatewayPaymentId, secret)` signature verification, the actual mechanism real gateways use). Swapping in a real gateway later means writing one new class and deleting the mock-complete dev route — nothing else in the module changes.
- `payments` is **not** unique on `orderId` — a failed attempt is a legitimate, retryable outcome, not an error state to overwrite. `orders.paymentStatus` always reflects the most recent attempt.
- `verify()` updates the `payments` row and the order's `paymentStatus` together in one transaction (the same "cross-table business operation" shape as Order's own status-transition method) — a payment can never end up `SUCCEEDED` while its order stays `PENDING`. Re-verifying an already-processed payment is rejected outright (idempotency against double submission).
- A `mock-complete` dev-only endpoint stands in for "the browser was redirected back from the gateway's hosted checkout with a payment id + signature" — it generates that payload server-side (where the secret actually lives) and then runs it through the *exact same* `verify()` a real callback would hit, so the real verification code path is genuinely exercised, not bypassed.
- Admin oversight here too (new `payments:read` permission, `GET /admin/payments`) — same reasoning as Orders.
- Frontend: a `PaymentPanel` on `/orders/:id` — "Pay ₹X" → initiate → clearly-labeled mock checkout ("Simulate successful/failed payment") → reflects the result. New `/admin/payments` read-only table.
- **First real Playwright visual verification in five sessions**: after repeated skips due to low RAM, a scripted walkthrough (seed a refresh token into `localStorage`, then click through menu → add-to-cart → cart → checkout → pay) confirmed the entire Modules 10–12 UI chain renders and behaves correctly end-to-end, not just compiles.

**Module 13 — Payment Webhooks** (`src/modules/webhooks`)
- The reliability backstop Module 12's synchronous `/verify` doesn't have: if a customer's browser never calls back (closed tab, dropped connection, device dies right after paying), the order would otherwise stay `PENDING` forever even though the gateway actually captured the payment. `POST /webhooks/payments` is `@Public()` and authenticated by an `X-Webhook-Signature` header instead of a JWT — a genuinely new auth pattern — verified as `HMAC-SHA256` over the **exact raw request bytes**, which required enabling Nest's raw-body capture (`rawBody: true`) at bootstrap; any JSON re-serialization before verification would silently break a real gateway's signature, a common real-world integration bug. Uses its own `PAYMENT_WEBHOOK_SECRET`, separate from Module 12's client-checkout secret, matching how a real gateway issues these independently.
- **Claim-then-process idempotency**: `webhook_events` is unique on `(gateway, gatewayEventId)`, and that constraint — not an application-level check — is what makes a redelivered event (normal at-least-once gateway delivery semantics) a 200 no-op instead of a double-apply. A webhook racing the synchronous `/verify` path for the same payment is handled the same way `verify()`'s own idempotency guard works: whichever one lands first wins, the second is a no-op.
- Extracted the payment+order transactional update (previously only inside `verify()`) into one shared private method both entry points call — same "don't duplicate a cross-table business operation" principle as everywhere else in the codebase.
- A `mock-send` dev-only endpoint builds a correctly-signed payload and runs it through the *real* `processPaymentWebhook()` in-process (not an HTTP self-call) — same "exercise the real code path, don't bypass it" approach as Module 12's `mock-complete`.
- Every delivery is logged regardless of outcome — valid, invalid, duplicate, or processing-failed — an append-only audit trail in the same spirit as `restaurant_status_history`/`order_status_history`, just logging an *external* event hitting the system instead of an internal state change. Admin oversight reuses the `payments:read` permission (`GET /admin/webhooks`) rather than adding a new one — webhook deliveries are payment-domain infrastructure, not a separate resource.
- Frontend: `/admin/webhooks` — a read-only delivery log (event type, gateway, outcome, processing error if any). Deliberately **no customer-facing UI** — webhooks are invisible infrastructure from a customer's perspective in a real system, so duplicating Module 12's "simulate payment" buttons with a second "simulate via webhook" control would just be confusing without adding anything a real user would ever see.

**Module 14 — Refunds** (`src/modules/refunds`)
- Found a real, concrete gap before designing this: **cancelling a `PAID` order never triggered any money back to the customer** — `OrdersService`'s cancellation methods never looked at `paymentStatus` at all. A restaurant could cancel an order the customer already paid for and the money would just stay taken. This module closes exactly that hole.
- **Event-driven, not a direct dependency** — Orders gained a new `order.status_changed` event (emitted only after a transition commits), and `RefundsService` listens for it, acting only when `toStatus === CANCELLED` and the order's `paymentStatus === PAID`. This is the *exact same decoupling shape* as Module 4's restaurant-approval-starts-a-trial listener — Orders stays completely unaware Refunds exists.
- The gateway interface gained a `refund()` method (mocked, same realistic-shape-but-fake pattern as Modules 12–13). The external call happens *outside* any DB transaction (an API call can't be rolled back); its outcome — success or failure — is what gets recorded, not assumed. A refund is its own row, not a mutation of the original `payments` row: a payment succeeding and its later refund are two separate financial events.
- On success, `order.paymentStatus` flips to `REFUNDED`; a failed gateway refund call is recorded as a `FAILED` refund row (visible to admin) rather than thrown away or silently retried forever. Only full refunds of `order.totalAmount` — partial/manual refunds for other reasons (bad food, missing items) are a reasonable future module, deliberately not built here.
- Admin oversight reuses `payments:read` (`GET /admin/refunds`) — same domain-grouping reasoning as Webhooks.
- Frontend: the order detail page (`/orders/:id`) shows a "Refunded ₹X" banner when applicable, reusing the existing `PaymentPanel` rather than a new page; `/admin/refunds` — a read-only log.
- Verified the real gap end-to-end: customer pays → restaurant confirms → restaurant cancels → order automatically flips to `REFUNDED` with a `SUCCEEDED` refund row, all without either side explicitly "issuing" anything.

**Module 15 — Ledger** (`src/modules/ledger`)
- The running per-restaurant balance: what the platform currently owes each restaurant, right now. Note **"Marketplace Split" is already effectively done** — Order (Module 11) already computes and snapshots `commissionAmount`/`restaurantPayoutAmount` via `CommissionService` (Module 5) at checkout time. This module is what turns those per-order numbers into a running balance restaurants can actually see.
- **Single-entry, signed-amount bookkeeping**, not full double-entry — `ledger_entries.amount` is positive for a credit, negative for a debit, so a balance is always a plain `SUM(amount)`, computed fresh on every read rather than stored/cached anywhere it could drift out of sync with its own entries.
- **Event-driven a third time**, same decoupling shape as Module 14: `PaymentsService` gained a `payment.succeeded` event and `RefundsService` gained a `refund.succeeded` event (both emitted only after their transaction commits); `LedgerService` listens to both — crediting `order.restaurantPayoutAmount` on payment success, debiting the *exact same amount* (not the customer's full refund, which includes the platform's commission) on refund success. Neither Payments nor Refunds knows Ledger exists.
- Both events fire at most once per payment/refund by construction — the upstream `CREATED`-only guards already established in Modules 12–14 prevent `applyOutcome`/`initiateForOrder` from ever running twice for the same row, so Ledger needed no separate idempotency check of its own.
- New `ledger:read` permission (rather than reusing `payments:read` like Webhooks/Refunds) — a restaurant's running balance is central enough to the business to warrant its own admin permission.
- Frontend: `/restaurant/ledger` (balance stat card + entry history, credits green/debits red) and a `LedgerModal` on `/admin/restaurants`, matching the Commission/Categories/Products modal pattern — Ledger is inherently restaurant-scoped, so it fits the per-row-modal shape better than a platform-wide list like Orders/Payments/Webhooks/Refunds.
- Verified end-to-end: two paid orders credit twice, cancelling one debits exactly what it credited, balance nets back correctly, admin's view matches the restaurant's own, and a second restaurant's ledger stays completely isolated.

**Module 16 — Customer Home Page** (`src/modules/{food-categories,banners,offers,blogs,favorites,notifications,store}`)
- Built ahead of its position in the module sequence, at explicit user request, as a complete customer-facing storefront home page before continuing to Settlement/Payout. Seven new backend modules plus one `Restaurant.isFeatured` flag, all admin-manageable CMS-style content — nothing on the page is hardcoded.

**Module 17 — Settlement** (`src/modules/settlements`)
- The periodic step between Module 15's Ledger (a running balance — what's owed, right now) and Payout (the next module — actually transferring the money). Running a settlement locks in every currently-*unsettled* `ledger_entries` row for a restaurant into one immutable `settlements` record, then stamps those exact entries with the new settlement's id so the next run can never double-count them.
- `Settlement` deliberately has **no status/workflow field** — it's a calculated fact, not a task. Whether the money has actually moved is Payout's job to track later, against its own table referencing this one.
- The read (sum unsettled entries) and the write (create settlement + stamp entries) happen in **one transaction** — the same shape as every other cross-table business operation in this app — so a ledger entry created mid-run can never be read into the sum but miss being stamped, or vice versa. Zero unsettled balance is a legitimate no-op (`null` return, not an error), not a `404`/`400`.
- New `ledger:manage` permission (mutating — trigger a run) alongside the existing `ledger:read` (viewing) — the same `:read`/`:manage` pairing convention Module 16 introduced for content types, now applied to Ledger's own admin capabilities.
- A weekly `@Cron(CronExpression.EVERY_WEEK)` runs settlements for every restaurant with an unsettled balance automatically; `POST /admin/settlements/run-all` and `POST /admin/restaurants/:id/settlements/run` exist for a manual/off-cycle/demo trigger without waiting a week — both call the exact same service method the cron does.
- Emits a new `settlement.created` event after each run commits (same decoupled shape as every other cross-module signal in this app) — for Payout, the next module, to listen to.
- Frontend: `/admin/settlements` (platform-wide list + a "Run settlements now" button) and `/restaurant/me/settlements` → `/restaurant/settlements` (own history), plus a "Run settlement now" button added to the existing per-restaurant `LedgerModal` on `/admin/restaurants` (gated on `ledger:manage`) so an admin can act on one restaurant right where they're already looking at its balance.
- Verified end-to-end against the real running server: a real paid order credits the ledger → running a settlement locks in exactly that balance → the settlement amount matches the ledger balance exactly → an immediate second run is a correct no-op → both the restaurant's own view and admin's platform-wide view show it → a non-admin is `403`'d from triggering a run.

**Module 18 — Payout** (`src/modules/payouts`)
- The step Settlement deliberately left out: actually executing the transfer. `Payout` is 1:1 with `Settlement` (`settlement_id` unique) — same "two separate financial facts" reasoning as Refund being its own row rather than mutating Payment: "money was calculated as owed" and "money was actually sent" are distinct events even though tightly coupled here.
- **A new gateway interface, not a method bolted onto `PaymentGateway`**: `PayoutGateway`/`PAYOUT_GATEWAY` (own DI token) + `MockPayoutGateway` (always succeeds, same shape as every other mock in this app). A restaurant bank payout is a genuinely different real-world integration from customer checkout/refunds (e.g. Stripe Connect Transfers vs. Stripe Checkout) even under the same vendor, so it gets its own interface.
- **Fully event-driven, zero manual trigger needed for the happy path**: listens for Module 17's `settlement.created` event and immediately creates + executes a payout — Settlements stays completely unaware Payouts exists. The external gateway call happens outside any DB transaction (an API call can't be rolled back); its outcome (`SUCCEEDED`/`FAILED`) is what gets recorded, not assumed — a failed transfer is a visible `FAILED` row, not silently dropped or retried forever.
- `POST /admin/payouts/:id/retry` (only valid on a `FAILED` payout, `409 PAYOUT_NOT_FAILED` otherwise) re-executes the exact same gateway call — for when a real bank transfer bounces and ops needs to retry without waiting for another settlement cycle. Reuses Settlement's `ledger:read`/`ledger:manage` permissions rather than adding new ones — payouts are squarely part of that same admin capability area.
- A defensive idempotency guard (check-then-create on `settlementId`) protects against ever double-executing a payout for the same settlement, even though the upstream event fires at most once by construction — same "belt and suspenders" pattern as other event listeners in this app.
- Verified end-to-end against the real running server, extending Module 17's own smoke test: real order → payment → ledger credit → settlement run → **payout auto-creates and auto-succeeds via the mock gateway within the same request's event cycle**, amount matches the settlement exactly, both restaurant and admin views show it, retry on an already-succeeded payout is correctly refused (`409`), and a second (no-op) settlement run creates no second payout.
- Frontend: `/admin/payouts` (platform table with a "Retry" button per failed row) and `/restaurant/payouts` (own history) — new sidebar nav items in both portals and a restaurant-dashboard quick-action tile.

**Module 19 — Delivery Partner (registration & profile)** (`src/modules/delivery-partners`)
- The `DELIVERY_PARTNER` role has existed since Module 2 with no module behind it — this gives it one, mirroring Module 3's Restaurant registration/approval shape (same lifecycle state machine, same status-history audit table, same `:read`/`:approve`/`:manage` permission triple) with one structural difference: `delivery_partners` is a **1:1 extension of `users`** (unique `user_id`, like `customer_profiles`), not an organization-with-staff table like `restaurants` — a delivery partner IS one person, so there's no "owns many staff" relationship to model. Created atomically at registration (like Restaurant), not lazily on first access (unlike CustomerProfile) — there's no meaningful "just the role, no profile yet" state.
- `POST /delivery-partners/register` creates the user + profile (`PENDING`) atomically and auto-logs in, same shape as restaurant registration. Admin lifecycle `/admin/delivery-partners/:id/{approve,reject,suspend,block,reinstate,resubmit}` — identical `ALLOWED_TRANSITIONS` state machine as Restaurant's, with one addition: leaving `APPROVED` for any other status **forces `isOnline` back to `false`** — a suspended/blocked partner can't keep appearing available for deliveries.
- Self-service `/delivery-partner/me/*` (`DeliveryPartnerGuard`, identity-scoped like `CustomerGuard`): profile view/update, `PATCH .../online` (rejected with `409 DELIVERY_PARTNER_NOT_APPROVED` unless the partner is `APPROVED` — going offline is always allowed regardless of status), and `PATCH .../location` (lat/lng — feeds Delivery Assignment/Tracking, a later module in this same cluster).
- Verified end-to-end against the real running server: registration → duplicate-email `409` → can't go online while `PENDING` (`409`) → non-admin `403`'d from approving → admin approves → partner can now go online → location updates → admin suspends (forces offline) → admin blocks → reinstating a `BLOCKED` partner correctly `400`s (terminal) → status history shows all 3 transitions → admin's status-filtered list finds it.
- Frontend: `/register-delivery-partner` (mirrors `/register-restaurant`), `/delivery` (own dashboard — status banner, online/offline toggle, "share current location" via the browser Geolocation API, vehicle details), `/admin/delivery-partners` (status-filtered table with approve/reject/suspend/block/reinstate actions, mirroring `/admin/restaurants` without the per-row modals a delivery partner doesn't need yet). New footer/login links to the registration page; `/` and `/login` both route a `DELIVERY_PARTNER` to `/delivery` the same way ADMIN/RESTAURANT_* already route to their own portals.
- **Scope boundary, stated plainly**: this module is registration/approval/profile only. Order assignment, delivery fee calculation, live tracking, OTP-verified handoff, and the delivery partner's own ledger/payout pair are the spec's own separate later modules in this cluster — deliberately not built here, so this module ships as a complete, tested slice rather than a half-built everything.

**Module 20 — Delivery Assignment** (`src/modules/delivery-assignments`)
- Matches a `READY` order to the nearest online, `APPROVED` delivery partner — event-driven off Module 11's `order.status_changed` (only reacts when `toStatus === READY`), same decoupled shape as every other cross-module trigger in this app. Real Haversine distance (same formula as Module 16's `StoreService.haversineKm`) from the **restaurant's** coordinates (not the customer's — the partner picks up from the restaurant first) to each online partner's last-reported `currentLatitude/currentLongitude`.
- **Deliberately its own lifecycle, not entangled with `Order.status`**: `delivery_assignments` has its own `ASSIGNED → ACCEPTED → PICKED_UP → DELIVERED` state machine (plus `REJECTED`), completely separate from Module 11's order fulfillment status. A restaurant can still self-report `OUT_FOR_DELIVERY`/`DELIVERED` on the order directly (e.g. it does its own delivery, or no partner was available) without this module's involvement — the two state machines coexist rather than one replacing the other.
- **Rejection triggers automatic reassignment**: a partner rejecting immediately re-runs the same nearest-partner search, excluding everyone who already rejected this specific order and everyone currently occupied by another active (`ASSIGNED`/`ACCEPTED`/`PICKED_UP`) delivery — a partner can never be double-booked.
- **OTP-verified handoff**: a random 6-digit code is generated at assignment time, visible to the customer (`GET /customer/me/orders/:id/delivery`) so they can hand it to the partner; `PATCH /delivery-partner/me/assignments/:id/deliver` requires the matching code (`400 INVALID_DELIVERY_OTP` otherwise) — a "delivered" claim is never taken on trust alone.
- Ownership is enforced server-side on every partner action (`403` if the assignment isn't theirs) — ownership is resolved from the caller's own JWT `userId` → their `DeliveryPartner` row, never trusted from the request.
- No partners available (none online, none with a shared location, or the restaurant itself has no coordinates) is a legitimate no-op (`null`), not an error — the order just has no assignment yet.
- New `delivery_assignments:read` admin permission (a new capability area spanning both restaurants and delivery partners, so it gets its own permission rather than reusing either domain's).
- Verified end-to-end against the real running server with two delivery partners at different distances: real order → real payment → restaurant progresses to `READY` → **automatically assigned to the nearer of two online partners** → the far partner sees nothing and is `403`'d from acting on it → near partner accepts → picks up → wrong OTP rejected (`400`) → correct OTP confirms delivery → restaurant's own view and admin's oversight list both agree.
- Frontend: a `DeliveryPanel` on the customer's `/orders/:id` (status, partner name/phone once assigned, the OTP itself), an "Active deliveries" section on `/delivery` (accept/reject, mark picked up, an OTP-entry field to confirm delivery), and `/admin/delivery-assignments` (platform-wide oversight table).

**Module 21 — Delivery Fee** (`src/modules/delivery-fee`)
- Closes a TODO Module 11's own `Order.totalAmount` comment left open verbatim: "delivery fee ... will extend this later." `delivery_fee_settings` is a single-row platform config (same pattern as Module 4's `trial_settings`) — `baseFee`, `perKmRate`, and an optional `freeDeliveryAboveAmount` waiver.
- `DeliveryFeeService.calculate()` computes `baseFee + perKmRate × distance` using the same Haversine formula as Modules 16/20, from the **restaurant's** coordinates to the **delivery address's** coordinates (both newly relevant — `CustomerAddress.latitude/longitude` already existed since Module 9 but had no consumer until now). Falls back to a flat `baseFee` (no fabricated distance) whenever either side lacks coordinates — an honest gap, not silently defaulted to zero.
- Wired into `OrdersService.checkout()`: the fee is computed off `subtotal` alone and added to `totalAmount`, but **never touches `restaurantPayoutAmount`** — delivery fee is a delivery-domain charge, not food revenue, so the restaurant's commission split is computed exactly as before. The fee and the raw distance (`deliveryDistanceKm`) are both snapshotted onto the immutable `Order` row, same "never rewritten by a later change" principle as every other Order snapshot field.

- Verified end-to-end against the real running server: an address+restaurant pair with coordinates gets a real distance-based fee; a high-value order crosses the free-delivery threshold and pays nothing; an address without coordinates falls back to the flat base fee; an admin rate change takes effect on the very next checkout; a non-admin is `403`'d from changing settings; the cart's live preview matches the eventual order exactly.
- Frontend: a live fee/distance estimate + running total on `/cart` (updates as the delivery address selection changes), a subtotal/fee/total breakdown on the customer's `/orders/:id`, and `/admin/delivery-fee` (a simple settings form).

**Module 22 — Delivery Tracking** (extends `orders`, `delivery-assignments`)
- Deliberately thin rather than a new module directory — the underlying data already existed (`DeliveryPartner.currentLatitude/currentLongitude` since Module 19, updated via the partner's own "share current location" action) and mostly needed one missing piece plus a read surface, not a new subsystem.
- **The missing piece**: `CustomerAddress.latitude/longitude` had existed since Module 9 but was never snapshotted onto `Order` at checkout, even though every other delivery-address field was (Module 11). Added `Order.deliveryLatitude/deliveryLongitude`, populated at checkout — closing the same class of gap Module 21 closed for the fee calculation, and for the identical reason: computing anything against "where this order is going" shouldn't require joining back to a `customer_addresses` row that may since have been edited or deleted.
- `DeliveryAssignmentsService.findForOrderWithDistance()` extends the existing assignment lookup with a `distanceRemainingKm` — the same Haversine formula as Modules 16/20/21, between the order's snapshotted delivery point and the partner's last-reported location — computed only when both exist, `null` otherwise (never fabricated). Both the customer's and the restaurant's existing delivery-status endpoints (Module 20) now return this automatically.
- No map library exists in this stack, so tracking stays text/coordinate-based ("3.2 km away") rather than a fabricated map UI — an honest scope boundary, not an oversight.
- Verified end-to-end against the real running server: a fresh order's snapshot includes real delivery coordinates, the assigned partner's distance-to-customer computes correctly, and the restaurant's own tracking view agrees exactly with the customer's.
- Frontend: `DeliveryPanel` (customer `/orders/:id`) now shows "📍 X km away from you right now" whenever an active assignment has a computable distance, and **lightweight polling** (`setInterval` every 15s while the assignment is in `ASSIGNED`/`ACCEPTED`/`PICKED_UP`, stopped automatically once `DELIVERED`/`REJECTED`) so the customer sees a live-ish view without manually reloading.

**Module 23 — Delivery Partner Ledger & Payout** (`src/modules/delivery-partner-ledger`) — last piece of the Delivery cluster
- The delivery-partner equivalent of Modules 15/17/18's Ledger/Settlement/Payout, but **deliberately a simpler two-table design** rather than three: a flat admin-configurable `perDeliveryRate` has no commission-split complexity to lock in independently of the transfer itself, so one `DeliveryPartnerPayout` does what Settlement and Payout did together for restaurants — sums every not-yet-paid-out ledger entry, stamps them, and executes the transfer, all in one step.
- Event-driven off a new `delivery.completed` event, emitted from `DeliveryAssignmentsService.deliver()` only after the OTP-verified `DELIVERED` transition commits — `DeliveryPartnerLedgerService` credits the flat rate automatically; Delivery Assignments stays completely unaware this module exists.
- Same "lifetime earnings" balance semantics as the restaurant ledger (Module 15): balance is `SUM(all entries)` always, a payout stamps entries as paid but never debits the displayed total — a deliberate consistency choice, not a new inconsistency invented here.
- Reuses Module 18's exact `PayoutGateway`/`MockPayoutGateway` (a restaurant bank payout and a delivery partner payout are both "transfer money to this person's bank account" in the mock world, so one gateway interface legitimately serves both) and its `PAYOUT_NOT_FAILED` retry-rejection error. New `delivery_partner_ledger:read`/`delivery_partner_ledger:manage` permissions.
- Verified end-to-end against the real running server: a fresh partner's ledger starts at ₹0.00, completing a delivery credits the exact configured rate with an entry referencing that specific assignment, a payout run sums+creates+auto-succeeds via the mock gateway, an immediate second run correctly no-ops, the displayed balance is unchanged after payout (matching the restaurant ledger's own semantics), and a non-admin is `403`'d from viewing another partner's ledger.
- Frontend: an "Earnings" section on `/delivery` (lifetime balance + entry history, paid/pending indicator per entry), a "Run payout" button per approved partner on `/admin/delivery-partners`, `/admin/delivery-partner-payouts` (platform table + "Run payouts now" + retry-on-failed), and `/admin/delivery-partner-fee` (the pay-rate settings form).

**Module 24 — Coupons** (`src/modules/coupons`) — the real, checkout-integrated redemption half of what Module 16's `Offers` deliberately left as display-only
- **Kept as a wholly separate `coupons` table rather than retrofitting `offers`**: Offers is a content-management concept (`content:manage`, admin-curated homepage copy) with zero redemption tracking; bolting per-customer/per-total usage limits and a row-locked redemption transaction onto it risked regressing an already-shipped, tested display feature for a financial one. A new dedicated `coupons:read`/`coupons:manage` permission pair, matching Ledger/Delivery-Fee's precedent that a checkout-critical money feature is "central enough" to warrant its own permission rather than reusing `content:*`.
- Two tables: `coupons` (code, PERCENTAGE/FIXED discount + optional min-order/max-discount-cap, optional restaurant scope, per-customer limit, optional total-redemption limit, optional starts-at/expires-at window, isActive) and `coupon_redemptions` (one row per successful redemption, `order_id` UNIQUE — a coupon is redeemed at most once per order).
- **The real enforcement happens inside `OrdersService.checkout()`'s own transaction**, not the standalone preview: `CouponsService.validateAndLock()` takes the transaction's `EntityManager`, row-locks the coupon (`SELECT ... FOR UPDATE`) before counting existing redemptions, so two concurrent checkouts racing a near-exhausted per-customer or total limit serialize instead of both succeeding. The redemption row itself is created right after the order saves (it needs the order's generated id) and inside the same transaction — a coupon-validation failure throws before the order is ever created, so the customer's cart is never cleared on a rejected coupon.
- A separate `CouponsService.preview()` runs the identical validation logic unlocked, non-transactional, against the live cart — a convenience for the cart page's live discount display, not a reservation; the real checkout re-validates from scratch regardless of what the preview showed.
- Discount computation: PERCENTAGE is `subtotal × value / 100`, capped by `maxDiscountAmount` if set; FIXED is the value itself; either way, never allowed to exceed the subtotal (so `totalAmount` can never go negative even before the delivery fee is added back on top). `Order.discountAmount`/`Order.couponCode` are snapshotted at checkout — same "never re-derive a money figure later" rule as `commissionAmount`/`deliveryFee`. `totalAmount` is now `subtotal + deliveryFee - discountAmount`.
- **Deliberate scope simplification, flagged rather than silently assumed**: the platform absorbs 100% of every coupon's discount — commission is still calculated off the full pre-discount subtotal, so a restaurant's `restaurantPayoutAmount` is completely unaffected by a coupon being used, whether the coupon is platform-wide or restaurant-scoped. A "who funds this discount" split (restaurant-funded vs. platform-funded coupons) would need real ledger/settlement wiring and is left for a future enhancement rather than guessed at now.
- Admin-only management (mirrors Offers — restaurant self-service coupon creation isn't exposed, avoiding scope creep): full CRUD at `/admin/coupons` plus `/admin/coupons/:id/redemptions` for oversight. Customer-facing surface is `GET /customer/me/orders/coupon-preview?code=X` (declared before `:id`, the same route-order rule as every prior `:id`-adjacent literal route) and an optional `couponCode` on the existing checkout call — no new customer endpoint needed since a redeemed coupon shows up on the order itself.
- 206 backend tests passing (29 suites, up from 188/28). Full live smoke test against the real running server (25 assertions): platform-wide coupon discount computed correctly, restaurant-scoped coupon rejected against a different restaurant's cart (`COUPON_NOT_APPLICABLE`), expired/unknown/inactive codes all correctly rejected, non-admin blocked from creating a coupon, real checkout applies the discount without touching the restaurant's payout, re-using an already-exhausted per-customer-limit coupon is rejected and — critically — does NOT clear the customer's cart (confirming the transaction actually rolled back), checkout without any coupon still works normally, admin's redemption list shows exactly the one real redemption, and deactivating a coupon immediately blocks further use.
- Frontend: `/admin/coupons` (full CRUD modal form + a "Redemptions" button per row opening a redemption-history modal) with a new sidebar nav item; `/cart` gained a "Have a coupon code?" input with live Apply/Remove and a green discount line in the totals breakdown (auto-clears with a re-apply prompt if the cart's subtotal changes underneath an already-applied coupon, since the discount was computed against a subtotal that's no longer current); `/orders/:id` shows the same coupon-code/discount line on any order that used one. Verified visually via Playwright: admin coupon list + create-modal, cart before/after applying a 20%-capped-at-₹60 coupon (600 → 540, cap correctly applied), and the resulting order detail page — zero console errors.

**Module 25 — Reviews** (`src/modules/reviews`) — the real star ratings every "no fake ratings" comment since Module 16 was waiting for
- One review per DELIVERED order (never per-product — an order can span multiple products, and every other "fact locked in at completion" pattern in this app is order-level too): overall 1–5 rating + optional comment, plus an optional restaurant response. `reviews.order_id` is UNIQUE (enforced by the DB, not just app logic) and `restaurant_id` is denormalized from the order at creation time purely so the rating-aggregate queries never join back through `orders`.
- **`ReviewsModule` has zero module-level dependencies beyond `TypeOrmModule`** — it injects the `Order` repository directly (read-only: ownership + `DELIVERED`-status checks) rather than importing `OrdersModule`, the exact "avoid growing another module's service for a storefront-adjacent read" pattern `StoreModule` already established for Module 16. This was a deliberate design choice, not an oversight: it's what lets `RestaurantsModule` AND `StoreModule` both safely import `ReviewsModule` for rating summaries without creating a circular dependency back through `OrdersModule → RestaurantsModule`.
- New dedicated `reviews:read`/`reviews:manage` permissions — a trust & safety moderation capability over user-generated content, a genuinely different kind of "admin oversight" than Offers/Banners' own `content:manage` (which is 100% admin-authored copy).

Normalized it to match everything else while adding ratings.

**Module 29 — Audit Logs** (`src/modules/audit-logs`) — a global interceptor, not a curated set of manually-instrumented call sites
- Distinct on purpose from the domain-specific history tables already built (`restaurant_status_history`, `order_status_history`, `subscription_events`, `delivery_partner_status_history`) — those record one entity's own lifecycle; this records *every authenticated mutating request platform-wide*, regardless of which module it hit. Considered manually adding `auditLogService.record(...)` calls to a handful of "sensitive" admin services instead, but a global `AuditLogInterceptor` (registered as `APP_INTERCEPTOR`, right alongside the existing `ResponseInterceptor`) gives complete, drift-proof coverage with zero changes to any existing service — a curated allowlist would silently miss the next sensitive endpoint someone adds later, and would need updating every time one does.
- Fires only for `POST`/`PUT`/`PATCH`/`DELETE` from an authenticated user (`req.user` populated by the JWT guard, which always runs before interceptors in Nest's request lifecycle) — GETs are reads, not actions, and an unauthenticated mutating request (e.g. restaurant registration) has no actor identity to record anyway. `/auth/*` is excluded entirely: login/register/refresh/password-reset are authentication plumbing, not business actions, and carry the highest risk of a redaction gap ever leaking a credential.
- Logs the matched **route pattern** (`request.route.path`, e.g. `/api/v1/admin/coupons/:id`), not the literal URL with a random UUID in it — the same id showing up as a thousand distinct-looking rows would make the log useless for "how often does this endpoint get hit" style review; the specific entity affected is still recoverable from `metadata` (the request body) when relevant.
- `actorEmail`/`actorRole` are denormalized snapshots taken from the JWT at request time, not FKs to `users` — an audit trail has to stay readable exactly as it happened even if the actor's account is later renamed, role-changed, or hard-deleted (not that this app allows hard-deleting users today, but the log shouldn't depend on that never changing).
- **Redaction, not just "log everything"**: a small denylist (`password`, `newPassword`, `currentPassword`, `token`, `rawToken`, `refreshToken`, `accessToken`, `tokenHash`) is stripped from the request body before it's ever written to the `metadata` jsonb column — one level deep, since every DTO in this app is a flat object. Combined with excluding `/auth/*` entirely, this closes the two realistic paths a credential could otherwise leak into a database column meant for admin-facing display.
- **Write failures can never break the real request**: `AuditLogsService.record()` catches and logs its own errors rather than propagating them — the exact same "a logging failure must never break the business action it's recording" principle `NotificationDispatchService` already established in Module 26. The interceptor itself never awaits the write inline either (`void this.auditLogsService.record(...)`), so a slow audit-log insert can't add latency to the request it's describing.
- New dedicated `audit_logs:read` admin permission (`GET /admin/audit-logs`, filterable by `actorUserId`/`method`/`path` substring, capped at the 500 most recent rows) — a genuinely new oversight capability, not folded into anything existing.

**Module 30 — Security Hardening** (`backend/src/main.ts`, `common/utils/production-safety.util.ts`) — scoped conservatively, one real deferral documented rather than silently skipped
- **A genuine latent misconfiguration found and fixed, not hypothetical**: `app.enableCors({ origin: process.env.CORS_ORIGIN?.split(",") ?? ## Mobile app — SDK 54 downgrade + real device verification — 2026-08-23

The user asked to actually run the app on a real phone via Expo Go. This surfaced (and fixed) a chain of real bugs that Playwright's web-only verification could never have caught, ending in the app genuinely running on real native infrastructure for the first time.

**Getting a phone onto the dev server at all, with no admin rights on the dev machine and no paid accounts:**
- LAN mode needs a Windows Firewall inbound rule; the user's account has no admin rights on this machine (confirmed by two separate `New-NetFirewallRule` "Access is denied" failures even after correctly elevating) — ruled out.
- Expo's own `--tunnel` (ngrok-based) worked for the JS bundle but ngrok's free/anonymous tier allows only one simultaneous tunnel per session — the app also needs a second tunnel for direct API calls to the backend, which ngrok's free tier refused ("remote gone away").
- **Landed on Cloudflare quick tunnels** (`npx cloudflared tunnel --url http://localhost:PORT`) — free, anonymous, no account, no single-tunnel limit; ran two simultaneously (one for Metro on :8081, one for the backend API on :4000).
- **A real Expo bug this exposed**: Expo's dev server doesn't know it's being tunneled by an external process, so it kept embedding its own literal listening port into every URL it handed the client (`https://<tunnel>:8081/...`) — meaningless to Cloudflare's edge, which only ever terminates on 443. Fixed with the (deprecated but functional) `EXPO_PACKAGER_PROXY_URL` env var, which overrides the advertised host/port entirely; confirmed by inspecting the raw manifest response before and after.

**The actual "project is incompatible with this version of Expo Go" error** — nothing to do with tunnels at all: the public Expo Go app (App Store/Play Store) only supports **SDK 54**; this project was on **SDK 57**. Confirmed via live web search rather than guessed, since this dev environment's software versions run ahead of the assistant's own training data. SDKs 55–57 currently require `eas go` (a custom Expo Go build via EAS, needing an Expo account) — the user opted to downgrade the project to SDK 54 instead, to keep working in the plain Expo Go app with zero external accounts.

**The downgrade itself (`npx expo install expo@54` + `npx expo install --fix`) surfaced a chain of pre-existing, unrelated bugs that had never been reachable before, because only the web bundle target had ever actually been exercised:**
- npm's strict peer-resolution rejected a `react-native-reanimated`/`react-native-worklets` peer range that was, in practice, satisfiable — resolved with `--legacy-peer-deps` (a routine, low-risk practice in the RN/Expo ecosystem, whose peer-dependency hygiene lags real compatibility). **Side effect worth remembering**: `--legacy-peer-deps` also suppresses npm's peer *auto-install*, silently leaving `react-native-worklets` — a real, needed runtime peer — not installed at all; had to be added back explicitly.
- **A genuine native-bundle-only bug, invisible to every prior web-only check**: the iOS/Android bundle failed to compile at all (`Unable to determine event arguments for "onModeChange"`) — a version mismatch between the root's correctly-versioned `@react-native/codegen` and an older copy nested inside `babel-preset-expo`. Fixed by upgrading `babel-preset-expo` to its SDK-matched release, after which the nested copy disappeared entirely (now resolves to the shared root version). **This is why the "no native build has ever been run" gap flagged in the previous session's writeup mattered — it wasn't cosmetic risk, it was hiding a real, unrelated compile failure the whole time.**
- **A recurring class of npm-workspace hoisting bug, hit three separate times across this whole mobile effort** (`expo-modules-core`/`jest-expo` earlier, then `react-native-css-interop`/`react-native`, then implicitly again with `react-native-worklets`): a package gets hoisted to the workspace root while a peer it directly `require()`s stays nested under `mobile/node_modules`, which Node's upward-only module resolution can never bridge. The durable fix this time: add the nested-only package explicitly to the **root** `package.json` (here, `"react-native": "0.81.5"` under root devDependencies) so npm has a reason to hoist a single shared copy every consumer can see — a full clean reinstall (`rm -rf node_modules` at both root and `mobile/`, then reinstall) was needed to get a consistent tree; incremental targeted installs kept leaving stale nested/hoisted patchwork behind.
- A stale `"expo-status-bar"` entry in `app.json`'s `plugins` array (harmless under SDK 57, broken under SDK 54 + Node 24's stricter native TypeScript handling) crashed startup entirely — removed; `expo-status-bar` never needed a config-plugin entry in the first place, unlike `expo-router`/`expo-secure-store`, which genuinely do.
- One transient real OOM crash during this process (both dev servers and Node itself died simultaneously) — recovered by restarting backend, then mobile, waiting for each to settle rather than immediately hammering it with verification requests.

**Net result**: clean `tsc --noEmit`, all 19 Jest tests still passing, a clean Metro web bundle, and — for the first time — the app actually running inside real Expo Go on a real phone, confirmed by the user directly. `mobile/AGENTS.md` and this section are the record of why SDK 54, not 57 — don't "fix" this back to a newer SDK without re-confirming what Expo Go's app-store build currently supports.
